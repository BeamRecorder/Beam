# Plan d’implémentation autonome — `packages/capture`

> **Périmètre : Rust uniquement.**
> Aucun code Vue, Electron, Canvas, rendu, zoom, motion blur ou export final dans ce plan.
> Ce package fournit le moteur natif, les exécutables de contrôle, les sidecars et les métadonnées nécessaires à l’interface future.

---

## 0. Résultat attendu

À la fin du plan, le dépôt contient un package Rust `packages/capture` capable de :

* détecter les capacités et permissions de la machine ;
* lister les sources sélectionnables :

  * écrans ;
  * fenêtres lorsque l’OS le permet ;
  * applications lorsque l’OS le permet ;
  * sorties audio système lorsque l’OS permet de les choisir ;
  * microphones ;
  * webcams ;
* enregistrer simultanément, au choix :

  * un écran ou une fenêtre ;
  * l’audio système ;
  * un microphone choisi ;
  * une webcam choisie ;
  * une piste de curseur séparée ;
* exclure le curseur de la vidéo lorsque la piste de curseur séparée est activée ;
* écrire chaque piste dans des sidecars indépendants ;
* identifier chaque projet et chaque session avec des UUID ;
* conserver des timestamps monotones exploitables par l’éditeur ;
* démarrer et arrêter proprement toutes les pistes ;
* gérer pause/reprise par segmentation, sans réécrire les médias précédents ;
* signaler les frames perdues, interruptions, changements de périphériques et erreurs ;
* être pilotable sans interface par des exécutables JSON/JSONL ;
* passer `cargo fmt`, `cargo test` et Clippy sans avertissement ;
* disposer de tests de logique obligatoires dans `tests/`, avec une hiérarchie miroir de `src/`.

### Non-objectifs

Ne pas implémenter ici :

* la timeline ;
* la composition des pistes ;
* les ombres ou arrière-plans ;
* les zooms ;
* le lissage ou motion blur du curseur ;
* l’export Mediabunny ;
* l’IPC Electron final ;
* l’upload ou le partage.

Le futur éditeur ne fera que lire les sidecars, aligner les pistes avec leurs timestamps, appliquer les effets et exporter.

# 1. Décisions techniques

## 1.1 Capture écran par OS

Utiliser une façade commune avec une implémentation native par système :

| OS        | Backend principal                              | Rôle                                                            |
| --------- | ---------------------------------------------- | --------------------------------------------------------------- |
| Windows   | `windows-capture = 2.0.0`                      | Windows Graphics Capture / DXGI, sélection d’écran ou fenêtre   |
| macOS     | `screencapturekit`                             | ScreenCaptureKit, écrans, fenêtres, applications, audio système |
| Linux     | `pipewire = 0.10.0` + XDG ScreenCast Portal    | flux écran/fenêtre sous Wayland et PipeWire                     |
| Linux X11 | PipeWire si disponible, sinon module X11 isolé | capture et curseur XFixes                                       |

### Choix macOS

Commencer avec la crate `screencapturekit`.

Exemple :

```toml
screencapturekit = { version = "8", features = ["macos_13_0"] }
```

Avant implémentation, l’agent doit vérifier la version disponible et les features exactes avec :

```bash
cargo search screencapturekit
cargo info screencapturekit
```

Si la crate choisie ne permet pas proprement :

* la capture écran ;
* la capture fenêtre ;
* la capture application ;
* l’audio système ;
* l’accès aux timestamps natifs ;
* l’accès aux surfaces sans copie CPU inutile ;

l’agent doit comparer avec :

```toml
screen-capture-kit = "0.7.1"
```

La décision finale doit être documentée dans `ARCHITECTURE.md`.

Conserver toute utilisation de cette crate derrière :

```text
src/screen/mac/
```

Le backend doit être remplaçable sans modifier l’API publique commune.

---

## 1.2 Audio

Utiliser :

```toml
cpal = "0.18.1"
```

CPAL sert à :

* lister les microphones ;
* identifier le microphone choisi ;
* inspecter les formats supportés ;
* capturer le microphone ;
* recevoir les événements de périphérique lorsque supportés ;
* unifier le modèle audio commun.

### Limite importante

CPAL ne rend pas automatiquement l’audio système générique.

L’audio système reste natif par OS :

| OS      | Audio système                                              |
| ------- | ---------------------------------------------------------- |
| Windows | WASAPI loopback                                            |
| macOS   | sortie audio fournie par ScreenCaptureKit                  |
| Linux   | node ou monitor PipeWire correspondant à la sortie choisie |

La façade publique sera générique, mais l’implémentation restera dans :

```text
src/audio/system/win/
src/audio/system/mac/
src/audio/system/linux/
```

---

## 1.3 Webcam

Utiliser de préférence :

```toml
nokhwa = {
  version = "0.10",
  default-features = false,
  features = ["input-native"],
}
```

Avant de verrouiller la version :

```bash
cargo search nokhwa
cargo info nokhwa
```

Objectifs :

* lister les caméras ;
* choisir une caméra ;
* lister les formats, résolutions et FPS ;
* ouvrir un flux ;
* horodater les frames ;
* enregistrer la webcam dans un sidecar vidéo indépendant.

Les adaptations de permissions et comportements propres aux OS restent dans :

```text
src/camera/win/
src/camera/mac/
src/camera/linux/
```

## 1.4 Concurrence

Éviter un runtime async global dans le cœur du moteur.

Utiliser :

* threads dédiés par backend ;
* channels bornés ;
* callbacks natifs ;
* annulation explicite ;
* RAII pour fermer les flux.

Dépendance commune recommandée :

```toml
crossbeam-channel = "0.5"
```

Exception Linux : le portail XDG peut utiliser un runtime Tokio minimal, compilé uniquement sous Linux.

---

## 1.5 Encodage d’enregistrement

Séparer strictement :

```text
capture native
    ↓
timestamps
    ↓
writer de piste
    ↓
sidecar
```

Définir une interface `VideoTrackWriter` afin de ne pas lier le moteur à un encodeur unique.

Backends visés :

### Windows

* encodeur matériel fourni par `windows-capture` si suffisant ;
* ou Media Foundation ;
* conserver les textures Direct3D aussi longtemps que possible ;
* éviter toute copie RGBA CPU inutile.

### macOS

* VideoToolbox pour H.264 ou HEVC ;
* AVAssetWriter ou équivalent pour le conteneur ;
* conserver les `CMSampleBuffer`, `IOSurface` ou pixel buffers natifs ;
* éviter toute conversion BGRA CPU inutile.

### Linux

* encodeur matériel disponible via :

  * VAAPI ;
  * V4L2 ;
  * NVENC ;
* premier backend acceptable :

  * processus FFmpeg contrôlé par Rust ;
* fallback logiciel autorisé ;
* aucun fallback vers Electron.

Le backend FFmpeg doit être optionnel et isolé. Il ne doit jamais contaminer les types du cœur.

### Format vidéo recommandé

Pour la première version :

* H.264 High ;
* MP4 fragmenté ;
* keyframe toutes les 1 à 2 secondes ;
* timestamps conservés ;
* débit configurable ;
* dimensions natives ;
* nouvelle séquence ou segment si les dimensions changent.

Le format fragmenté limite la perte de données si le processus s’arrête brutalement.

---

## 1.6 Audio sidecar

Pour la première version fiable :

* WAV PCM float 32 bits ;
* fréquence native du périphérique ;
* nombre de canaux natif ;
* fichiers segmentés pour éviter les limites de taille ;
* aucun mixage micro/système ;
* aucun resampling destructif pendant la capture.

Chaque segment possède son propre `start_ns` dans le manifeste.

Une feature FLAC pourra être ajoutée plus tard sans changer le modèle de piste.

---

## 1.7 Curseur

Le curseur doit être une piste indépendante.

Enregistrer :

* timestamp monotone ;
* position normalisée dans la source capturée ;
* position en pixels de la source ;
* visibilité ;
* boutons ;
* ID de forme ;
* bitmap de la forme ;
* hotspot ;
* changement d’écran ou de crop ;
* événements de clic.

Backends :

### Windows

* `GetCursorInfo` ;
* `GetIconInfo` ;
* extraction du bitmap ;
* extraction du hotspot ;
* boutons souris ;
* gestion des curseurs monochromes et colorés.

### macOS

* position globale ;
* forme ;
* hotspot ;
* AppKit ou autre API native disponible ;
* gestion des permissions nécessaires.

### Linux Wayland

* demander le mode curseur `Metadata` au portail ;
* lire les métadonnées PipeWire ;
* détecter si le compositor ne fournit pas ce mode ;
* renvoyer une capacité explicite au lieu de faire semblant.

### Linux X11

* XFixes pour la forme ;
* position ;
* hotspot ;
* visibilité.

Ne jamais enregistrer uniquement un enum :

```rust
Arrow
Hand
IBeam
```

Les curseurs personnalisés doivent être conservés comme bitmap.

## Règles d’arborescence

* Aucun import `windows::*` hors d’un dossier `win/`.
* Aucun import `windows_capture::*` hors d’un dossier `win/`.
* Aucun import `screencapturekit::*`, AppKit ou API Apple hors d’un dossier `mac/`.
* Aucun import `pipewire::*`, `ashpd::*` ou X11 hors d’un dossier `linux/`.
* Les modules communs ne contiennent aucun gros bloc de logique `#[cfg(target_os = ...)]`.
* Les fichiers `mod.rs` ne contiennent que les exports et un minimum de wiring.
* Limite visée : **500 lignes par fichier**.
* Un test d’architecture doit échouer si un fichier de `src/` dépasse 500 lignes.
* Une exception doit être ajoutée dans une allowlist explicite et documentée.
* Aucun fichier généré dans `src/`.
* Les binaires délèguent toute logique à la bibliothèque.
* Les dossiers `tests/` doivent refléter les responsabilités de `src/`.

## Remarques sur les dépendances

* `anyhow` est autorisé dans les binaires, exemples ou outils.
* `anyhow` ne doit pas être utilisé dans l’API publique de la bibliothèque.
* La bibliothèque utilise des erreurs typées avec `thiserror`.
* `unsafe` n’est autorisé que dans les backends OS.
* Chaque bloc `unsafe` doit posséder un commentaire `SAFETY:`.
* Ne pas ajouter `tokio` comme dépendance commune.
* Ne pas ajouter `ffmpeg-next` comme dépendance commune.
* Ne pas ajouter de framework GUI.
* Ne pas ajouter de dépendance de rendu.
* Si FFmpeg est utilisé sous Linux, préférer un processus contrôlé et isolé.
* Vérifier les licences des dépendances dans `THIRD_PARTY.md`.

# 4. Modèle public

## 4.1 Identifiants

Utiliser des newtypes, jamais des `String` anonymes :

```rust
use uuid::Uuid;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct ProjectId(Uuid);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct SessionId(Uuid);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct TrackId(Uuid);

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct SegmentId(Uuid);

#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct SourceId(String);
```

Créer les projets et sessions avec UUID v7 pour conserver un ordre temporel naturel.

## 5.3 Écriture atomique

Pendant l’enregistrement :

* écrire dans `manifest.partial.json` ;
* écrire le curseur en JSONL append-only ;
* écrire les événements de santé en JSONL ;
* écrire les ancres temporelles en JSONL ;
* écrire les médias par segments ;
* fsync aux points importants ;
* ne jamais réécrire un gros fichier média.

À l’arrêt propre :

1. fermer les backends ;
2. arrêter les callbacks ;
3. drainer les queues ;
4. finaliser les writers ;
5. finaliser les index de pistes ;
6. convertir `cursor.partial.jsonl` en `cursor.json` ;
7. écrire `manifest.json.tmp` ;
8. renommer atomiquement vers `manifest.json` ;
9. supprimer `manifest.partial.json` seulement après réussite.

Au redémarrage, `storage::recovery` doit pouvoir reconstruire une session partielle.

# 6. Horloges et synchronisation

## 6.1 Règle absolue

Ne jamais synchroniser les pistes uniquement avec :

```rust
SystemTime::now()
```

Utiliser :

* QPC et timestamps WGC sous Windows ;
* host time et PTS ScreenCaptureKit sous macOS ;
* PTS PipeWire sous Linux ;
* timestamps de callback CPAL lorsque disponibles ;
* une horloge monotone de session pour les événements internes.

---

## 6.2 Session clock

Créer un `SessionClock` commun :

```rust
pub trait MonotonicClock: Send + Sync {
    fn now_ns(&self) -> u64;
}
```

Chaque backend fournit un `TimestampMapper` :

```rust
pub trait TimestampMapper {
    type NativeTimestamp;

    fn to_session_ns(
        &mut self,
        native_timestamp: Self::NativeTimestamp,
    ) -> Result<u64, CaptureError>;
}
```

---

## 6.3 Barrière de démarrage

Ordre obligatoire :

1. valider les sources ;
2. vérifier les permissions ;
3. vérifier l’espace disque ;
4. créer les dossiers ;
5. créer tous les writers ;
6. préparer tous les backends ;
7. attendre que chaque backend soit armé ;
8. définir `t0` ;
9. lancer les backends ;
10. écrire le premier anchor de chaque piste ;
11. passer l’état à `Recording`.

Si une piste obligatoire échoue avant `t0`, tout annuler proprement.

---

## 6.4 Dérive

Ne pas resampler automatiquement dans la première version du moteur.

Écrire périodiquement dans `timing.jsonl` :

```json
{
  "trackId": "uuid",
  "sessionNs": 12000000000,
  "nativePosition": 576000,
  "nativeRate": 48000
}
```

L’éditeur pourra mesurer et corriger la dérive au rendu.

# 7. Machine à états

```text
Idle
  -> Discovering
  -> Preparing
  -> Armed
  -> Recording
  -> Paused
  -> Recording
  -> Stopping
  -> Finalizing
  -> Completed
```

États d’erreur :

```text
Preparing -> Failed
Recording -> Degraded
Recording -> Failed
Finalizing -> Recoverable
```

Règles :

* aucune transition implicite ;
* toutes les transitions testées ;
* `stop()` idempotent ;
* `Drop` déclenche une fermeture best-effort ;
* pause/reprise crée de nouveaux segments ;
* un device hot-unplug produit un événement explicite ;
* la `FailurePolicy` décide si une piste optionnelle peut mourir sans arrêter la session.

```rust
pub enum FailurePolicy {
    FailFast,
    ContinueWithoutOptionalTracks,
}
```

---

# 8. Pipeline et backpressure

Chaque piste dispose d’une queue bornée.

Ne jamais utiliser une queue non bornée pour les frames.

```rust
pub struct QueueConfig {
    pub capacity: usize,
    pub overflow: OverflowPolicy,
}
```

```rust
pub enum OverflowPolicy {
    DropNewest,
    DropOldest,
    StopSession,
}
```

### Politique recommandée

#### Écran et webcam

* `DropNewest` ou `DropOldest` selon le backend ;
* compteur obligatoire ;
* événement de santé ;
* aucune croissance mémoire non bornée.

#### Audio

* ne pas jeter silencieusement ;
* créer une discontinuity ;
* signaler une erreur de santé ;
* écrire la durée ou le nombre de samples perdus.

#### Curseur

* coalescer les mouvements consécutifs ;
* ne jamais perdre les clics ;
* ne jamais perdre les changements de forme ;
* ne jamais perdre la visibilité.

Le callback natif ne doit jamais :

* bloquer sur le disque ;
* encoder de manière synchrone ;
* sérialiser du JSON ;
* attendre un mutex long ;
* envoyer une frame complète par stdout ;
* appeler Electron ;
* effectuer une copie CPU non nécessaire.

* interdit les `cfg` OS dispersés dans le code commun ;
* interdit l’accès direct à une API native depuis les binaires.

### API publique

* vérifier que seuls les types souhaités sont publics ;
* utiliser `unreachable_pub` ;
* documenter tout item public ;
* éviter les structs fourre-tout ;
* éviter les enums non exhaustifs sans justification.

# 11. Qualité et performance

## 11.1 Règles de code

* fonctions courtes ;
* responsabilités uniques ;
* pas de singleton global mutable ;
* pas de lock tenu pendant un callback externe ;
* pas de `unwrap` dans `src/` ;
* pas de `expect` dans `src/` ;
* pas de panique pour une erreur runtime ;
* erreurs avec contexte ;
* types distincts pour :

  * pixels ;
  * coordonnées normalisées ;
  * nanosecondes ;
  * sample positions ;
  * dimensions ;
  * FPS ;
* pas de conversion implicite entre timestamps ;
* pas de sérialisation dans les callbacks temps réel ;
* pas de copie de frame sans justification mesurée ;
* pas d’allocation par sample audio lorsque cela peut être évité ;
* aucun log dans un callback haute fréquence sauf rate limiting.

* dépendances par target ;
* features optionnelles ;
* pas de Tokio commun ;
* pas de `ffmpeg-next` commun ;
* pas de framework GUI ;
* pas de codec logiciel compilé si non utilisé ;
* pas de dépendance de rendu ;
* pas de dépendance web.

```

```

# 16. Vision de l’intégration future

Le moteur Rust crée uniquement les pistes brutes et leurs métadonnées :

```text
screen.mp4
camera.mp4
system-audio.wav
microphone.wav
cursor.json
cursor-shapes/
manifest.json
timing.jsonl
```

L’interface future pourra ensuite :

1. ouvrir le manifeste ;
2. charger les pistes ;
3. les aligner grâce à `session_ns` ;
4. jouer les pistes ensemble ;
5. dessiner le curseur séparément ;
6. appliquer :

   * smoothing ;
   * motion blur ;
   * click effects ;
   * zooms ;
   * crop ;
   * ombres ;
   * arrière-plans ;
7. exporter la composition finale.

Le moteur Rust ne doit jamais connaître :

* le motion blur ;
* les zooms ;
* la timeline UI ;
* les ombres ;
* le fond ;
* les transitions ;
* Mediabunny ;
* Canvas2D.

Sa seule responsabilité est de produire des pistes natives, séparées, fiables, synchronisées et récupérables.
